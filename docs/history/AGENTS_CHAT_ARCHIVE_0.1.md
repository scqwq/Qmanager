# QQArchive — Agent 实现约定与第一版开发任务

> 文档版本：0.1；起草日期：2026-10-03。
> 项目状态：从零开始，尚无经验证的 NTQQ Reader 或可发布产品。
> 本文件应放在仓库根目录，供开发 agent 在开始工作、规划任务及修改代码前阅读。
> 本文是项目目标、实现边界、初始任务和验收契约；不能把规划中的能力描述为已经实现。

## 1. 项目的真实目标

用户的 QQ 历史记录和图片、视频、文件占用大量磁盘，但无法确定以后是否仍需查阅，因此不敢直接删除。手工压缩并上传云盘又缺少群聊、日期和内容索引，后续难以找到所需备份，也难以记住原文件应放回哪里。

QQArchive 的长期目标是管理 QQ 聊天记录的生命周期：按账号、会话和时间选择数据，生成可验证、可独立查阅的归档，将旧数据放到用户选择的存储位置，在具备可靠备份与经过验证的清理机制后释放本机空间。

第一版只完成这条链的前半段：**读取 → 选择 → 归档 → 校验 → 独立打开与搜索 → 用户自行上传。**

用户无需记忆底层路径。产品应让用户按“某账号、某群聊、某时间段”寻找归档。不要把项目实现成只有文件夹选择器和压缩按钮的工具，也不要将主要精力放在无关的社交聊天功能上。

长期目标不等于第一版承诺。第一版不会自动减少 QQ 数据的磁盘占用，创建归档还会临时增加占用；必须在界面和文档中诚实说明。

## 2. 第一版的成功定义

第一版版本标识为 v0.1，面向 Windows 上的 NTQQ 本地数据。先验证一个明确的 QQ 版本与数据库结构，再逐步扩展，不承诺兼容所有历史 QQ、移动端 QQ 或所有 NTQQ 版本。

用户可以：

1. 手动选择 QQ 测试副本，或从有限范围内发现候选数据目录。
2. 在只读访问下连接受支持的数据源；明确看到账号、来源路径和兼容性状态。
3. 查看可识别的群聊/私聊，选择一个会话和日期范围。
4. 预览消息数、已定位媒体大小、缺失媒体、未支持类型和估算空间。
5. 导出一个自描述的 `.qqarc` 包，不依赖 QQ 原目录即可打开。
6. 对包结构、文件哈希、消息关系及数据库进行校验，获得真实的完整性报告。
7. 将导出的包自行上传到任意云盘、复制到移动硬盘或 NAS。
8. 日后选择下载回来的包，直接在 QQArchive 中查看文字和图片、搜索文字，不需要恢复进 QQ。
9. 即使本地 catalog 被删除，也能仅凭归档包重建该归档的展示信息。

必须同时完成真实数据验证和软件流程验证。只有合成数据/明文 SQLite 演示时，应标为开发演示，不能宣称 NTQQ 已适配。

## 4. 对此前技术讨论的修订

此前提出的技术路线作为候选方案，不能当成已验证事实：

- 优先研究 VFS/兼容加密数据库的只读访问，但不得写死页大小、偏移、密钥派生、数据库字段或表名。具体行为必须依据目标版本、可信实现及实际副本验证。
- VFS 不是自动解决 WAL、一致性和加密兼容性的万能层。解密快照 Reader 可以作为调试或兼容备用方案，其额外空间和隐私成本必须明确。
- “SELECT 可以成功”只证明有限读取可行，不证明图片映射、消息解析和完整归档已经成立。
- 第一版“恢复”指在 QQArchive 中重新打开归档，不能将其称为“恢复 QQ 聊天记录”。
- `.qqarc` 是具有规定结构的 ZIP64 容器，不是自行发明加密或压缩算法。
- 手动上传后程序不知道云端对象是否完整，禁止自动产生 `CLOUD_VERIFIED` 或 `SAFE_TO_REMOVE` 状态。
- 保存原相对路径只提供来源线索，不保证未来能够无损注入 QQ。
- SHA-256 校验可以检测损坏；无法单独证明源数据齐全、来源真实或内容未被恶意改写。
- 已存在于源端的缺失图片不能通过导出补回。归档应准确保留这种缺失状态。
- 会话归属大小和实际可释放空间不是同一指标，共享媒体尤其不能重复承诺释放。

## 5. 不可违反的数据安全边界

### 5.1 QQ 源数据始终只读

不修改、不删除、不移动、不重命名源文件，不修改数据库内容、索引、日志、账号配置或媒体。禁止对源数据库执行写入 SQL、迁移、VACUUM、checkpoint 或会产生源文件变化的 PRAGMA。

源层公开读取接口，不暴露可随意执行 SQL 的 UI/API。使用数据库只读打开标志、只读事务和文件访问策略形成多层保护。不能仅靠代码中暂时没有 DELETE 来宣称只读。

不要为了成功打开数据库把源端 WAL/SHM 删掉、复制回去或强行让 QQ 退出。不要自动结束 QQ 进程。

### 5.2 开发优先使用一致的副本

首先使用合成数据和用户自行准备的测试副本。复制前通常应由用户正常关闭 QQ；同时考虑数据库、WAL、相关数据库和媒体，不应把运行中复制单个 `.db` 当作一致快照。

如实现在线只读访问，必须验证目标版本下的锁、VFS、WAL 可见性和读取一致性。无法证明时，停止导出并提示使用关闭 QQ 后准备的副本，不得静默忽略 WAL 或使用 `immutable` 绕过实际变化。

媒体也可能在读取过程中变化。导出计划记录源标识与必要指纹；流式复制时核对读前/读后状态及大小。发现变化则标记不稳定或重新规划，不能将混合时间点数据标为一致快照。

### 5.3 输出与源路径必须隔离

导出目录、暂存目录、cache、日志、catalog 均不能位于 QQ 源根目录内。校验真实路径、大小写、卷路径、符号链接与 Windows junction，避免通过路径别名绕过限制。对于重叠或无法判断的路径，拒绝写入并说明原因。

禁止导出时覆盖已存在的包。使用唯一暂存名，校验完成后再发布最终文件；用户明确选择替换自己的归档时也要保证失败不损坏原包。

清理仅能作用于应用拥有的暂存/cache，范围必须可证明，不能跟随链接进入源目录或用户其他文件。

### 5.4 不提供清理授权状态

v0.1 不含“释放 QQ 空间”“已安全删除”“可删除源数据”按钮、命令、接口或状态。不得根据包哈希通过自动建议用户删除 QQ 数据。后续清理功能需独立研究、实现与验收，不继承本版本归档成功作为删除授权。

## 6. 隐私、密钥和外部项目

- 数据处理默认在本机进行，无聊天内容遥测、自动上传或远程分析。
- 不把账号、群名、消息、媒体、密钥和真实数据库提交到 Git、公开 issue 或 CI artifacts。
- 日志默认只记录任务 ID、错误码、计数和脱敏路径，不打印消息正文、完整账号、数据库密钥或原始记录。
- 密钥输入为隐藏字段，默认只在当前会话内使用；不存 localStorage、普通配置或归档。
- 缓存数据库连接或解密快照必须具有明确生命周期，任务结束关闭句柄；临时明文须放在受限应用目录，不承诺 SSD 上“安全擦除”。
- v0.1 包默认可能包含明文聊天与附件，导出界面明确提示其隐私属性。不要宣称 ZIP 压缩提供加密保护。
- 不实现自创密码学。加密归档如进入后续范围，应使用成熟认证加密格式并单独定义密钥恢复策略。
- 自动 KeyProvider 如研究，限定用户自己的账号与明确启动的连接流程；第一版不引入进程注入、绕过系统权限或提权服务。
- 研究 QQLore、QQNT_Export 等外部实现前检查当前代码、支持版本、许可证与依赖。名称只是研究线索，不等于已授权复制或已经兼容。
- 许可证不明或不兼容的代码不可直接复制。记录上游版本、链接、许可证及修改，保留所需声明。

## 7. 初始技术栈与验证要求

候选基线：Go 核心、Wails v2 桌面桥接、Vue 3 + TypeScript 前端、SQLite 自有数据、ZIP64 归档。前端构建工具随受支持的 Wails 模板选择，避免无必要重写脚手架。

这些是设计选择，不是对当前最新版状态的断言。初始化时查阅官方文档，确认所选稳定版本、Windows 构建环境、WebView2、Go/Node 版本和 SQLite 驱动能力，并固定版本与 lockfile。

特别验证：

1. NTQQ Reader 与 VFS 是否需要 CGO/原生库，Windows 打包是否可重复。
2. 自有 SQLite 驱动与加密 Reader 是否冲突；可分层或用独立 helper，避免让整套应用依赖未验证的混合驱动。
3. FTS5 是否实际启用。中文检索需真实样例验证，不假定默认分词能够满足中文子串查询。
4. ZIP64 大文件、Windows Unicode/长路径、非默认磁盘、可移动存储与中断行为。

优先完成 CLI/core 的真实只读技术验证，再投入完整桌面 UI。若环境仅能运行 Linux 核心测试，Windows build/runtime 仍列为未验证，不声称桌面验收通过。

## 9. 核心接口原则

先明确职责，再根据实测实现精简接口。所有长任务接受 `context.Context`，支持取消；消息分页/迭代读取，禁止把整库加载进内存。

可采用如下概念接口，签名需在实现时补足错误与一致性语义：

```go
type Reader interface {
    Describe(ctx context.Context) (SourceInfo, error)
    Conversations(ctx context.Context) ([]Conversation, error)
    Iterate(ctx context.Context, q MessageQuery, emit func(RawMessage) error) error
    Close() error
}

type Parser interface {
    Parse(ctx context.Context, raw RawMessage) (Message, []Diagnostic, error)
}

type ArchiveBuilder interface {
    Plan(ctx context.Context, selection Selection) (ExportPlan, error)
    Build(ctx context.Context, plan ExportPlan, output string) (BuildResult, error)
}

type ArchiveVerifier interface {
    Verify(ctx context.Context, path string) (VerificationReport, error)
}
```

Reader 打开由 factory 完成，连接、密钥和关闭职责明确。NTQQ 的原始表结构不泄漏进 Vue，也不成为归档 schema。PlainReader 用同一领域边界验证归档流程。

不要现在实现完整 Cloud Provider。保留存储位置与导出产物的边界即可，避免创建大量未用的云盘接口和凭据表。

## 10. 数据模型与时间语义

### 10.1 标识与消息顺序

- 账号、群号、发送者 ID、消息 ID 按字符串跨桥传输，防止 JavaScript 大整数精度损失。
- ConversationKey 至少区分来源账号、会话类型和源会话 ID，不能只用群名称。
- 消息源 ID 不一定全局唯一；组合源身份、会话身份和稳定源定位形成去重键。无法可靠识别时保留冲突记录，不静默覆盖。
- 保留源时间值及其单位/解释，标准化为 UTC 时间，同时记录展示时区。
- 同一时间戳以源序号、稳定源定位等打破并列，不以文本哈希合并“重复”消息。
- 发送者历史名称和当前名称区分，无法解析的名称显示 ID 或“未知”，禁止虚构。

### 10.2 日期筛选

用户选择开始/结束日期，解释为指定时区内包含结束日期的整天。内部使用 `[start, endExclusive)`，结束边界为次日当地零点。记录时区名、UTC 边界与显示范围，禁止简单用 23:59:59 排除更高精度时间戳。

默认展示时区为用户系统时区，测试明确指定时区。日期边界、跨月跨年及夏令时必须测试。

### 10.3 原始记录与未支持类型

每条消息保留：源标识、会话、发送者、原时间、顺序、已解析内容段、源类型、解析器版本，以及归档范围内必要的原始字段/字节。

无法解析的类型仍占一条消息并显示占位，保留原始证据及诊断。不要把整个原 QQ 数据库塞进单会话包，造成其他会话隐私泄露。

引用或转发涉及范围外记录时，记录引用缺失或经明确规则纳入依赖；不要偷偷扩大用户选择范围。依赖纳入数量要在预览与报告中说明。

## 11. 媒体定位、去重与统计

媒体映射优先依据消息内部引用、资源标识及经验证的源规则。不能仅凭修改时间、扩展名或所在月份断言属于某个群。

媒体引用至少包含：消息键、内容段序号、媒体类型、资源 ID、已验证的源相对路径、原名称、定位状态、实际字节数、SHA-256、包内相对路径。不要把完整绝对源路径默认写进可分享的包。

状态区分 `present`、`missing_at_source`、`unresolved`、`unsupported`、`copy_failed`。缩略图与原图分开记录，只有缩略图时明确提示。

按实际复制出的字节 SHA-256 做包内 CAS 去重。多条消息可以引用同一对象；保持每一处引用。第一版只要求包内去重，不要求跨包共享媒体，否则破坏单包独立性。

统计应区分：

- 消息和媒体引用数量；
- 已找到的唯一对象数量与字节；
- 因共享媒体重复归属的逻辑大小；
- 实际包大小；
- 缺失/无法定位的引用数量。

找不到媒体大小时显示未知，不能算作 0 字节再标为完整。导出容量估算与实际值区分，不承诺压缩后大小，不显示“预计释放空间”。

## 12. `.qqarc` v1 格式契约

### 12.1 容器与结构

采用标准 ZIP64，扩展名 `.qqarc`，UTF-8 元数据。图片、视频等已压缩媒体优先 STORE，文本与数据库可用标准压缩；不可使用单流压缩导致打开一条消息必须解压全部媒体。

```text
manifest.json
messages.db
metadata/conversation.json
metadata/participants.json
media/sha256/<前两位>/<完整64位小写hash>
reports/export.json
checksums.json
```

媒体不依赖扩展名，真实 MIME 与原文件名存数据库。不要信任声明 MIME，渲染时仍需防护。

`messages.db` 是普通 SQLite，含归档范围消息、内容段、媒体对象、媒体引用及必要原始记录。打包前关闭连接并确保所有提交已落到主数据库；包内不依赖外置 WAL/SHM。

### 12.2 Manifest 必需字段

至少定义：格式标识 `qqarchive`、主版本/次版本、archive UUID、创建时间、导出器版本、来源类型、经验证的源 QQ 版本/结构指纹、解析器版本、账号标识、会话类型/ID/名称快照、时间边界与时区、筛选规则、消息数、已解析数、未支持数、媒体引用数、唯一对象数、缺失数、导出一致性方式、完整性状态、校验算法。

示例字段必须标为示例，不硬编码到实现。QQ 客户端版本无法获得时填 `unknown`，数据库结构指纹仍应记录。

主版本不支持时拒绝正常打开并保留原包，次版本新增字段按兼容规则处理。迁移只能写应用私有副本或新包，不修改导入的原包。

### 12.3 校验文件与循环哈希

`checksums.json` 列出包内所有有效载荷文件的路径、实际字节数及 SHA-256，包括 manifest、数据库和报告；不包含它自身。校验器要求实际条目集合与清单一致，拒绝重复路径、未列出的有效载荷及缺失条目。

整个 `.qqarc` 的 SHA-256 在包完全关闭后计算，可存 catalog 并向用户显示/复制。不要把“整个包哈希”嵌回包内产生循环依赖。用户手动上传后可记住该哈希，下载后程序重新计算；没有可信预期值时不能宣称与原上传文件一致。

各文件哈希与整包哈希都是损坏检测，不是签名或来源认证。

### 12.4 自描述与便携性

包必须包含独立查看所需的全部已获取内容、引用映射与版本信息。验证时将源目录设为不可访问，并使用空 catalog 打开。

源端本就缺失的附件可以保留占位，但完整性状态必须注明。不得读取原目录悄悄补图后将它作为独立性通过证据。

格式说明写入 `docs/ARCHIVE_FORMAT.md`，提供小型合成示例生成器，使未来无需原项目 UI 也能理解格式。

## 13. 导出与校验流程

1. 检查数据源兼容性和一致性能力。
2. 固定筛选范围，生成 ExportPlan，统计解析/媒体定位诊断。
3. 检查源与目标隔离、目标可写、可用容量与大文件限制；检查暂存和最终文件所需的峰值空间，不仅最终包大小。
4. 建立唯一应用暂存目录与任务日志。
5. 分页读取、解析消息，事务写入自有 SQLite；流式复制并哈希媒体。
6. 输出完整性报告；复制失败不能悄悄跳过。
7. 关闭自有数据库，执行 SQLite 完整性检查和领域关系核对。
8. 写元数据、manifest、校验清单，生成暂存 `.partial` 包。
9. 从生成的包重新读取并执行校验，确认独立打开。
10. 同卷发布最终文件；跨卷时先复制到目标同卷暂存并验证，再完成最终命名。记录平台文件系统限制，不承诺所有盘上绝对原子持久化。
11. 计算整包哈希并登记 catalog；登记失败不删已经完成的包，后续可重新导入。
12. 返回包路径、大小、真实报告和“可自行上传”说明。

区分两种结果：

- **结构与内容校验通过，支持范围内内容完整**：所有应获取的受支持内容成功复制，源缺失另行说明。
- **包可打开但内容有缺失/未支持**：报告明确列出原因与数量，不得展示绿色“全部无损”。

已有源缺失可由用户知情导出并保留占位；导出期间的新读取/复制错误默认使任务失败。若支持继续生成不完整包，须有明确选项与持久报告，不把它标为正常成功。

状态至少包含 `PLANNING`、`EXPORTING`、`PACKAGING`、`VERIFYING`、`READY`、`READY_WITH_WARNINGS`、`FAILED`、`CANCELLED`。状态、校验结果和用户手工备注是不同维度。`READY` 只代表本地归档结果。

任务取消要传播到读取、复制、数据库写入与压缩，关闭句柄，保留可解释的失败信息，不能产生看似完整的最终包。第一版支持重试即可，未经验证不要承诺断点续导。

## 14. 手动云盘工作流与本地 Catalog

第一版与云盘无账号绑定、无自动上传、无自动下载。用户自由选择云盘。

导出完成页面提供：打开所在文件夹、复制文件名、复制整包哈希、查看校验报告。用户自行上传。

可提供可选的“备份位置备注”，例如“某云盘/QQ归档/实验室群/2023”。备注属于用户填写的文本，不作为云端存在或完整性的证据，不自动访问链接，不存登录令牌。不要提供语义含糊的“已验证上传”开关。

本地 catalog 保存 archive ID、会话/时间摘要、当前位置、大小、已知整包哈希、校验时间与结果、用户备注。包被移动或删除时标为“本地包不可用/路径失效”，不得直接认定云端可用。

从其他机器或云盘下载的包可以重新导入；相同 UUID 但哈希不同应提示冲突，不静默替换或混合消息。catalog 可重建、可备份，不能是查阅归档的唯一依赖。

第一版只对本地可访问归档搜索。没下载的归档仅有摘要时，UI 不得表现为能够搜索其中消息。云端全文索引和按需媒体是未来能力。

## 15. 浏览器与搜索的安全要求

- 消息文本使用文本渲染，禁止直接 `v-html` 注入消息或合并转发内容。
- 超链接仅对允许的 http/https 等明确协议提供用户点击打开；禁止 javascript、任意 file 路径和自定义执行协议。
- 不自动下载远程消息资源，不让网页引用泄露用户 IP 或请求凭据。
- 只通过受控资源接口访问包内/cache 媒体；不能把任意磁盘路径暴露给 WebView。
- 附件不会自动执行；打开外部文件是用户明确动作，执行类文件有明显类型提示。
- 参数化查询；FTS 特殊语法与普通搜索分开，防止原样输入导致错误或意外查询。
- 中文搜索若采用 FTS5，验证实际分词与子串需求；允许第一版以受限分页 LIKE 提供可用搜索，说明性能边界，不宣称 FTS 已启用却不测试。
- 浏览分页、搜索分页，避免全量列表阻塞 WebView。UI 区分无结果、读取错误和未支持类型。

## 16. 打开不可信归档的防护

归档可能损坏或由第三方提供，不能信任它的文件名、长度和数据库。

拒绝绝对路径、盘符路径、UNC、`..`、路径规范化后越界、重复条目、链接条目及 Windows 设备名/ADS 等危险目标。第一版尽量不批量解压到用户目录，读取条目或仅解压到受控 cache。

限制条目数、manifest 大小、单文件大小、总展开大小及压缩比，按本机可用空间作检查。大媒体允许流式读取，不用小型固定限制误拒正常大包；限制值要有依据并可测试。

SQLite 以只读模式打开导入副本，禁用扩展加载，限制可执行查询，验证 schema 和字段；不能执行包内提供的 SQL、脚本或迁移代码。

展示报告前先校验结构，不把未验证 manifest 中的“通过”字段当结果。失败包保留原文件并给出原因，不自动“修复”或覆盖。

## 17. 第一版界面与交互

至少提供以下完整流程，而不是只做静态 Dashboard：

1. 数据源页：选择目录、候选账号、连接、密钥输入、兼容性与错误说明。
2. 会话选择页：名称/ID、消息范围、统计状态；数据不可知时显示未知。
3. 导出页：会话、日期范围、输出目录、预览、缺失清单、空间估算、明文包提示。
4. 任务页：当前阶段、已处理数量/字节、取消、失败后重试、完成报告。
5. 归档库：导入/定位包、会话与日期、大小、校验状态、本地路径是否有效、可选备份备注。
6. 查看页：消息时间线、发送者、文本、图片、未支持类型占位、搜索与跳转。

首次启动先让用户能够手动选择测试副本。自动发现可以后台有界执行，不阻塞整个界面，也不因未发现 QQ 而无法打开现有归档。

界面面向使用者，不要求理解 VFS、SQLCipher、WAL 或 CAS。详细诊断放到可展开区域，默认错误信息给出具体可执行步骤。

第一版不需要大规模统计图、AI 总结、主题系统、多账号同时导出、自动归档规则或云盘管理页面。

## 18. 从零开始的实施里程碑

### M0：工程初始化与范围固化

建立 Git 项目/脚手架（如当前已有仓库则保留）、依赖版本、目录、README、忽略规则、构建与测试命令。创建项目计划和进度文档。为真实数据库、密钥、归档、日志和个人目录配置忽略规则。

验收：核心最小程序和桌面壳在目标环境可运行，文档明确范围与已验证环境，没有个人数据进入仓库。

### M1：真实 NTQQ 只读技术验证

以测试副本完成：识别账号/目录 → 连接 → 读取结构 → 列出会话 → 读取指定会话最近少量消息 → 定位一张真实图片。记录数据库版本/结构指纹、密钥来源方式、一致性策略与所有限制。

禁止根据猜测编造 QQ 表结构。缺少真实副本或必要密钥时，继续合成 Reader 与归档模块，将真实兼容标为阻塞并说明具体需要，不伪造验证结果。

### M2：归档核心闭环

定义领域模型与包格式，实现时间筛选、文本与图片提取、原始记录保留、包内去重、校验、取消和失败清理。先通过 CLI 完成。

验收：一份合成包与一份真实测试包均可在源不可访问时读取；哈希与数量通过核对；缺失/未支持真实报告。

### M3：独立浏览、搜索与目录

实现只读包打开、有限 cache、catalog 登记/重建、消息分页、图片展示、中文搜索和源断开测试。

验收：新用户目录/空 catalog 中仅凭包即可查看；移动包后可重新定位；同名不同 ID 与同 UUID 冲突有正确行为。

### M4：桌面完整流程

连接 core 与 Wails/Vue，完成全部必要页面和任务反馈；UI 不要求命令行操作，不暴露源写入能力。

验收：Windows 上可从选择副本到导出、关闭程序、重新打开包、搜索全程完成；长任务可取消且 UI 有响应。

### M5：打包、故障验收与交付

生成可重复的 Windows 构建，记录运行依赖，完成损坏包、大文件、空间不足、非 ASCII 路径与中断检查，更新版本、变更记录和兼容表。

验收：干净目标环境中运行；已知限制明确；任何未跑的 Windows/真实数据检查列为未验证。

## 20. 性能与资源管理

- 消息迭代/分页、数据库批量事务、媒体流式读写与哈希，禁止一次读入整个附件。
- 有限 worker 池，默认保守并发，避免磁盘随机读取失控；不要为每个文件创建 goroutine。
- 清楚显示准备、复制、打包、校验各阶段，未知总量使用不定进度，不伪造百分比。
- 设置句柄、cache 和空间上限。cache 只能删自己的文件，原始包不随 cache 清理而删除。
- 避免暂存整套媒体后又额外复制多次；选择实现方案时记录峰值空间成本。
- 所有阶段检查取消，错误保留上下文但脱敏。
- 不设没有实测依据的“百 GB 秒开”目标。记录性能样本、机器环境、消息数、媒体量和实际时间。

## 21. Agent 日常工作规则

开始任务先读本文件及已有计划、进度、格式与兼容文档，检查代码和当前改动。尊重用户已有文件，不覆盖与当前任务无关的内容。

在已授权的第一版范围内自主推进常规可逆实现，不反复询问已确定的技术偏好。只在缺少真实数据、密钥、目标系统环境或存在无法推断的重要产品选择时，提出具体问题；同时继续不依赖该信息的工作。

先做完整可验收的纵向流程，再补功能。禁止长时间仅生成接口、漂亮假数据 UI 或空目录，而无实际归档行为。演示数据必须明显标记。

依赖当前事实的技术选择查官方文档；区分设计推断、代码阅读和实际验证。QQ 私有结构与加密参数尤其不能依赖模型记忆。

不自动推送公共仓库、发消息、上传个人数据、修改 QQ 或删除用户归档。本文没有授权这些动作。
